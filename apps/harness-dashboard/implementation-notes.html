Dashboard Redesign — Implementation Notes

This document records the design decisions, deviations, tradeoffs, and open questions for the harness-dashboard redesign from Three.js / R3F org chart (Stage3D) to a CSS-only OrgTree component backed by real .harness/documents/ data.

Design Decisions

1. CSS Flexbox + inline SVG for org tree — no D3 or react-flow

The harness hierarchy is fixed: Owner → CEO → 5 CXX → Workers. There is no runtime graph topology to discover, so a force-directed layout library would add significant bundle weight (react-flow: ~600kB) with zero benefit. The BranchConnector SVG uses percentage-based X positions that match the flexbox column centers by construction — no DOM measurements needed. If the hierarchy shape changes (e.g. a CEO deputy layer), the fixed layout can be extended without touching the SVG math.

2. Three.js / R3F components preserved — only the import in Scene.tsx is removed

All files under components/three/ are left intact. Stage3D and SceneFallback are no longer dynamically imported in Scene.tsx, but the source is not deleted. This preserves existing test coverage and leaves a migration path back to 3D if the product direction changes. The dynamic import overhead was only at runtime, not at build time, so removing it has no negative effect on build.

3. Mission documents served inline from snapshot — no per-click fetch

readMissions() in lib/harness-state.ts reads all .harness/documents/{"{"}mission-id{"}"}/ directories at snapshot time (same call that reads progress.json). The drawer tabs display document content from snapshot.missions without an additional round-trip. The SSE stream (/api/snapshot/stream) remains the single data source. Limit is 15 missions; worker files inside each mission are also read inline.

4. Workers shown under CTO column

In real harness usage (moon_web), workers are always dispatched via the CTO architecture plan's ## 워커 지시 section. The worker doc format (.harness/documents/{"{"}mission{"}"}/workers/{"{"}worker-name{"}"}.md) is produced by hired workers reporting back to CTO. Showing workers under the CTO card in the org tree is therefore semantically correct and matches the actual file structure.

Deviations from Spec

1. harness-cdo has no sub-agents in v7.1

deviation The spec mentioned harness-cdo but moon_web/.harness/config.json confirms CDO exists as a role but has no workers in AGENT_ROSTER or any agentIds. The CDO node is rendered with status="idle" and an empty agentIds array. This is the correct state for v7.1 — CDO is a placeholder for future design/branding agents.

2. .harness/meetings/ and .harness/workers/ don't exist in real moon_web

deviation The existing buildRecentMeetings() reads from .harness/actions/meetings/ (not .harness/meetings/). The real moon_web project has no such directory. The new readMissions() function supplements this by reading from .harness/documents/, which is where real v7 agent output actually lives.

3. CEO drawer shows actual ceo.md instead of a separate brainstorm file

deviation The "brainstorming decisions" in the CEO drawer now surfaces the actual .harness/documents/{"{"}mission{"}"}/ceo.md which contains ## CEO 결정 (routing decisions) and ## Owner 요청 요약. This is more accurate than attempting to parse a hypothetical separate brainstorm file that does not exist in the real harness output.

Tradeoffs

1. YAML frontmatter stripped by regex

tradeoff MissionDocTab strips YAML frontmatter using /^---[\s\S]*?---\n/ before rendering. A proper YAML parser (e.g. js-yaml) would be more robust, but adds a dependency and the frontmatter content is not rendered anyway — only stripped. The regex is sufficient for all observed harness document formats.

2. Branch connector SVG uses equal-width column assumption

tradeoff The SVG percentage widths assume that the five CXX flexbox columns are equally wide (same min-w-[150px] max-w-[190px] cards with gap-3). At very narrow viewports (below ~800px) or when workers push the CTO column significantly wider, the connector lines may not align perfectly with the actual card centers. A ref-based measurement approach (ResizeObserver + useLayoutEffect) would be more precise but adds React complexity. For the expected viewport range (1280px+), the equal-width assumption is accurate.

3. Missions sorted by directory mtime

tradeoff Missions are ordered by statSync(missionPath).mtime. If the OS modifies a directory's mtime for reasons other than harness writes (e.g. metadata updates, backup tools), the ordering could drift. An explicit timestamp in each mission's YAML frontmatter would be more reliable. The existing docs have updatedAt in frontmatter but parsing it would require stripping and reading YAML — added complexity for a correctness edge case that hasn't occurred in practice.

Open Questions

  1. open CDO sub-agents: Should we add "cdo" to AgentId type and AGENT_ROSTER once harness-cdo gains real sub-agents (design reviewer, brand auditor)? The OrgTree's CDO node already has agentIds: [] and getStatus([]) returns "idle" — no code change needed in OrgTree when agents are added, only in types.ts and agent-roster.ts.
  2. open feature-queue.json team slots as worker cards: The feature-queue.json has teams state (idle / busy). Should the OrgTree show team slots as worker mini-cards even when no .harness/documents/{"{"}mission{"}"}/workers/ file exists? Currently only workers with an actual .md file are shown. The queue-based workers are already surfaced in the WorkerPanel on the right side panel.
  3. open Truncated content in progress.log: The user-prompt | input lines in progress.log contain content truncated to ~100 chars by the harness hook. The readOwnerHistory() function reads whatever is written. Should we parse a separate source (e.g. the CEO mission doc's ## Owner 요청 요약 section) to get the full prompt content for the Owner History tab?
  4. open SSE watcher glob coverage: The SSE stream fires on .harness/ file changes via lib/watcher.ts. Verify that the watcher glob includes .harness/documents/** — if it only watches .harness/progress.json and .harness/actions/, new mission documents written by agents won't trigger a snapshot push. Check lib/watcher.ts and expand the glob if needed.
