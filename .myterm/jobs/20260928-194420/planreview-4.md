# MyTerminal 이슈 전달 문서 4차 설계리뷰

## 요약

진행 표시 방향은 타당하며, 이전 리뷰의 대상 목록 보존·재시작 복원·프로세스 식별·재중단 기준 변경도 반영됐습니다. 다만 새 대상의 영속화, 저장 실패 처리, 카드 삭제 경로에 중단 복구를 무력화하는 빈틈이 남아 있습니다. 이슈 전달 문서의 해당 절차를 보완한 뒤 구현해야 합니다.

## 지적 사항

### [HIGH] 종료 확인 중 새로 발견한 대상은 신호 전에 저장할 경로가 없음

- 위치: `ProcessScanner.killAndConfirm(_:sessionRoot:)` 설계 · “신호는 기록된 뒤에만 보냅니다” 규칙
- 문제: `killAndConfirm`은 세션 재탐색으로 새 대상을 발견하면 정지·종료하도록 되어 있지만, `freezeTree`와 달리 저장 콜백이 없습니다. 반환값에도 갱신된 대상 목록이 없습니다. 이대로 구현하면 새 대상에 SIGSTOP을 보낸 직후 앱이 종료됐을 때 그 대상이 디스크 기록에서 빠져, 설계가 보장한 복구 조건을 깨뜨립니다.
- 수정안: 재탐색에서도 기존 대상과 새 대상의 합집합을 저장한 뒤 신호를 보내도록 동일한 저장 경로를 사용합니다. 저장 실패 시 신호를 보내지 않고 미확인으로 남깁니다. 재탐색으로 추가한 대상에 첫 신호를 보낸 직후 앱이 종료되는 복구 테스트를 추가합니다.

### [HIGH] 저장 실패 시 차단 유지와 마무리 재개가 보장되지 않음

- 위치: `cancel` 3·5·6·7번, `confirmed` 복원 절차 · [PipelineRunner.swift](/Users/ted/project/myterminal/Sources/MyTerminal/Pipeline/PipelineRunner.swift:887)
- 문제: 최초 stop 파일 저장에 실패하면 `pendingStop`이 없는데, 마지막에 `stopping`까지 제거하므로 다음 tick과 재시도가 다시 열립니다. 또한 기존 `recordFailure`는 저장 오류를 내부에서 처리하고 성공 여부를 반환하지 않습니다. 이를 그대로 호출한 뒤 stop 파일을 삭제하면 실패 결과를 저장하지 못했어도 복구 기록이 사라집니다. 이는 “저장 실패는 미확인”, “마무리는 멱등하게 재개”한다는 규칙과 충돌합니다.
- 수정안: 최초 저장 실패에는 메모리의 미확인 차단과 오류 표시를 유지하는 경로를 명시합니다. 마무리는 결과 파일이 이미 존재하거나 실패 결과 저장에 성공했음을 확인한 경우에만 stop 파일을 삭제하도록 합니다. 최초 stop 저장 실패와 실패 결과 저장 실패를 각각 주입해, 차단 또는 `confirmed` 기록이 유지되는지 검증합니다.

### [HIGH] 카드 삭제가 중단 복구 기록을 통째로 제거함

- 위치: 변경 범위에서 빠진 `PipelineRunner.delete` · [PipelineRunner.swift](/Users/ted/project/myterminal/Sources/MyTerminal/Pipeline/PipelineRunner.swift:285), [JobCard.swift](/Users/ted/project/myterminal/Sources/MyTerminal/Home/JobCard.swift:240)
- 문제: 현재 카드 삭제는 창을 닫고 작업 폴더 전체를 삭제하며, 실행 중에도 접근할 수 있습니다. 설계는 중단·재시도 버튼만 제어하므로, 중단 중 또는 미확인 상태에서 삭제하면 `.stop.json`과 대상 목록도 사라집니다. 남은 프로세스를 복구할 근거가 없어지고, 진행 중인 중단 작업도 삭제된 폴더에 저장하려다 실패할 수 있습니다.
- 수정안: 최소한 `stopping` 또는 미해결 stop 기록이 있는 동안에는 UI와 `delete` 함수 양쪽에서 삭제를 막습니다. 미확인 상태에서 삭제를 요청해도 작업 폴더와 대상 목록이 보존되는 회귀 테스트를 추가합니다.

### [MEDIUM] 루트 PID를 못 찾은 상태에서는 “다시 중단”의 복구 절차가 정의되지 않음

- 위치: `cancel` 1·2·3번 · `StopRecord`의 `rootPid`, `rootStart`
- 문제: 창은 있지만 PID를 읽지 못하면 미확인 기록을 남기도록 했지만, 기록 구조는 루트 식별 정보를 전제로 합니다. 다음 중단은 `pendingStop`을 우선 사용하고, PID 조회는 “첫 중단”에만 수행합니다. 따라서 루트와 대상이 없는 기록을 어떻게 표현하고, 조회가 정상화됐을 때 어떻게 다시 수집할지 빠져 있습니다. 빈 대상 목록을 완료로 처리하거나 복구가 계속 막힐 수 있습니다.
- 수정안: 루트 미확보 상태를 명시적으로 표현하고, 재중단 시 해당 단계의 창에서 루트 식별을 다시 시도하도록 합니다. 루트 미확보와 대상 전체 종료를 구분하고, 첫 조회 실패 후 두 번째 조회 성공 시 정상적으로 수집·종료되는 테스트를 추가합니다.
