# MyTerminal 이슈 전달 문서 5차 설계리뷰

## 요약

새 대상의 신호 전 저장, 카드 삭제 차단, 루트 미확보 시 재조회는 이전 지적을 반영했습니다. 저장 실패 처리도 개선됐지만, 메모리 차단에서 재중단할 대상이 사라지는 경우와 결과 경로의 존재만으로 마무리를 성공 처리하는 문제가 남아 있습니다.

## 지적 사항

### [MEDIUM] 최초 저장 실패 후 단계가 끝나면 “다시 중단”이 동작하지 않음

- 위치: `stopBlocked: [String: String]`, `cancel` 1·3번 · [Job.swift](/Users/ted/project/myterminal/Sources/MyTerminal/Pipeline/Job.swift:802)
- 문제: 최초 stop 저장 실패 시 메모리에는 사유만 남습니다. 신호를 보내지 않았으므로 agent는 계속 실행하며 결과를 저장할 수 있고, `refresh`는 차단 중에도 실행됩니다. 결과에 따라 `activeStep`이 없어지면 재중단은 `pendingStop`도 `activeStep`도 없어 즉시 반환합니다. 화면에는 “다시 중단”이 표시되지만 재시도·삭제 차단을 해제할 방법이 없습니다. 성공 결과로 다음 단계가 활성화되면 중단 대상이 원래 단계에서 바뀔 수도 있습니다.
- 수정안: 최초 저장 실패 시에도 메모리에 사유와 함께 중단하려던 `step`, `round`, 확보한 `root`·`targets`를 보존합니다. 재중단은 디스크 기록, 메모리 기록, 현재 단계 순으로 대상을 정합니다. 저장 실패 후 agent 결과가 기록되어 phase가 바뀐 상황에서 원래 단계의 중단을 완료하고 차단을 해제하는 테스트를 추가합니다.

### [MEDIUM] 결과 경로의 존재만 확인하면 설계에 추가한 저장 실패 테스트를 통과할 수 없음

- 위치: `recordFailure -> Bool`, 마무리 저장 실패 테스트 · [PipelineRunner.swift](/Users/ted/project/myterminal/Sources/MyTerminal/Pipeline/PipelineRunner.swift:887)
- 문제: 현재 가드는 `fileExists(atPath:)`이며, 설계는 결과가 이미 있으면 `true`를 반환하도록 합니다. 테스트처럼 결과 경로에 같은 이름의 디렉터리를 만들면 이 가드가 참이 되어 저장을 시도하지 않고 성공 처리합니다. 따라서 `confirmed` 기록이 삭제되어야 한다는 구현 흐름과, 기록을 유지해야 한다는 테스트 기대가 충돌합니다. 실제로는 읽을 수 있는 결과가 없는데 복구 차단이 풀립니다.
- 수정안: 기존 결과를 보존하는 정책은 유지하되, 단순 경로 존재와 읽을 수 있는 결과 파일을 구분합니다. 디렉터리이거나 결과를 읽지 못하면 `false`와 오류를 반환하고 `confirmed`를 유지합니다. 이미 제시한 디렉터리 충돌 테스트로 이 조건을 검증합니다.
